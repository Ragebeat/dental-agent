# dental-agent

**LLM-агент, который записывает на приём, отменяет и переносит записи в стоматологической клинике. Сделан так, чтобы его можно было измерять, а не только показывать.**
Свой MCP-сервер, агент на LangGraph, Postgres, канал LINE, сводка владельцу, трассировка в Phoenix и стенд оценки с эталонными сценариями.

*Языки: [English](README.md) · Русский · [日本語](README.ja.md)*

> Тезис проекта не «бот записывает на приём», а: **мы измерили, как часто он записывает верно, и знаем, почему он ошибается.**
> Жёсткий критерий: **0 неверных записей и 0 дублей**. Его держит база данных, проверяет стенд.

Все данные синтетические. Это портфолио-проект, а не внедрение в настоящую клинику. Реальных пациентов, телефонов и медицинских систем здесь нет.

## Результаты

Набор разработки: 15 эталонных сценариев × 3 повтора = 45 диалогов на конфигурацию. Агент: `gemma4:e4b`, запущена локально (Ollama). Симулятор пациента: DeepSeek через OpenRouter. Исход проверяет код по итоговому состоянию базы, а не LLM-судья.

| Конфигурация | Верный исход | Неверные записи / дубли | Сработавшие атаки | Передача человеку: recall / precision | Токены агента на диалог |
|---|---|---|---|---|---|
| `baseline-v1` (один промпт и те же инструменты, свободный цикл ReAct) | 0,800 (36/45) | 0 / 0 | 0 из 6 | 0,78 / 0,88 | ~20 900 |
| `graph-v3` (LangGraph, промежуточная версия) | 0,933 (42/45) | 0 / 0 | 0 из 6 | 1,00 / 1,00 | ~60 |
| `graph-v6` (LangGraph, финальная), вызов напрямую | 0,978 (44/45) | 0 / 0 | 0 из 6 | 1,00 / 1,00 | ~50 |
| `graph-v6` через вебхук LINE (эмуляция) | 1,000 (45/45) | 0 / 0 | 0 из 6 | 1,00 / 1,00 | ~75 |

Как читать эти цифры честно:

- Сравнение baseline и графа сделано на одной версии стенда (после правок из DECISIONS №29). Прогоны до этих правок несравнимы и здесь не используются.
- 45 диалогов дают широкий доверительный интервал (около ±10 процентных пунктов). Разница между `graph-v6` напрямую (0,978) и через LINE (1,000) — один диалог шума симулятора, а не регрессия и не улучшение.
- Цифры получены на наборе **разработки**. Правила графа настраивались, пока я смотрел на него, поэтому цифры завышены. Отложенный набор и прогон на сильной облачной модели **ещё не сделаны** (см. [Статус и ограничения](#статус-и-ограничения)).
- Единственный проваленный диалог в прогоне `graph-v6` напрямую (s02, повтор 1) — сбой инфраструктуры, а не решение агента: локальный процесс Ollama упал с HTTP 500 на запасном вызове LLM (таких падений в прогоне два; второе, в s07, на исход не повлияло). Он засчитан как провал и оставлен в цифрах.
- Токены графа близки к нулю, потому что граф — детерминированный код: LLM вызывается только на узких запасных путях. Это замысел, а не трюк измерения.
- Журнал прогонов (`data/runs.jsonl`) хранит каждый прогон с отпечатком конфигурации (модели, хеш промпта, хеш схем инструментов, хеш конфига клиники, хеш сценариев), поэтому любые два прогона можно сравнить. Журнал закоммичен вместе с полными отчётами о диалогах четырёх прогонов из таблицы (`data/runs/*baseline-v1_ds-sim2*`, `*graph-v3_ds-sim2*`, `*graph-v6_web*`, `*graph-v6_line*`). Всё остальное в `data/` создаётся заново или остаётся локальным.

## Что он делает

Пациент пишет в клинику (основной язык японский). Агент:

1. определяет пациента по номеру карты и дате рождения (или регистрирует нового: имя, фуригана, телефон, дата рождения);
2. понимает намерение: записаться, отменить, перенести;
3. спрашивает недостающее (услуга, дата, время);
4. находит слоты кодом и предлагает до трёх вариантов;
5. **просит подтверждение у пациента** перед любой записью в базу;
6. пишет через инструменты MCP и сообщает результат;
7. передаёт человеку, когда нужно (медицинский вопрос, жалоба, поздняя отмена, неоднозначность, повторные сбои инструментов, подозрение на манипуляцию).

Модель клиники (синтетическая, в `clinic.toml` и базе): 4 кресла, слоты по 30 минут, пять услуг (первичный приём 初診, лечение 治療, проверка дёсен 歯周検査, чистка クリーニング, плановый осмотр 定期検診). Закрыто в четверг, воскресенье и японские праздники. Горизонт записи 60 дней (для чистки и осмотра 200 дней), не больше двух активных записей на пациента, бесплатная отмена не позднее чем за 24 часа.

## Архитектура

```
пациент ──► агент (LangGraph) ──► MCP-сервер (инструменты) ──► ядро записи ──► Postgres
   ▲              │                                                ▲
   │              └─► передача сотруднику                          └─ ограничения в базе
 вебхук LINE / стенд оценки / консоль

сводка владельцу ◄── факты (SQL/код) ─► текст LLM ─► проверка кодом ─► HTML
трассы: OpenTelemetry ─► Phoenix (по умолчанию выключено, содержимое скрыто)
```

**Принцип: LLM понимает текст и пишет связный текст, всё остальное делает детерминированный код.** Модель не считает даты, не решает, свободен ли слот, и не пишет в базу.

- **Ядро записи** (`dental/core`, без LLM, покрыто тестами). Операции: поиск слотов, запись, отмена, перенос, список записей, проверка личности, регистрация пациента. Двойную запись предотвращает **база данных**: исключающее ограничение (`EXCLUDE USING gist` по креслу и интервалу времени) для активных записей. Промпт такую гарантию заменить не может. Тест запускает 20 параллельных потоков на один свободный слот и ожидает ровно одну запись. Этот же тест нашёл настоящую взаимную блокировку параллельных вставок, она решена блокировкой на день (DECISIONS №21).
- **MCP-сервер** (`dental/mcp_server`). Инструменты: `list_services`, `search_slots`, `verify_identity`, `register_new_patient`, `get_my_appointments`, `book_appointment`, `cancel_appointment`, `reschedule_appointment`, `handoff_to_staff`. Один процесс сервера — один разговор и одна сессия; id пациента привязан к сессии, модель его не видит и не задаёт. Произвольного SQL нет. Ошибки осмысленные и с подсказками (`slot_taken` с ближайшими слотами, `outside_hours`, `too_late_to_cancel`, `patient_not_verified`, `limit_reached`). Вызовы записи несут ключи идемпотентности, поэтому повторный запрос не создаст вторую запись.
- **Агент** (`dental/agent/graph.py`, `GRAPH_VERSION = "graph-v6"`). Жёсткий конечный автомат на LangGraph, рассчитанный на слабую локальную модель. Правила в `understand.py` и `dates.py` разбирают сообщение пациента, включая относительные японские даты («来週の水曜», «明後日の夕方», «3か月後», «14時以降»): их считает код по текущей дате и календарю праздников (jpholiday). LLM — запасной путь только для узких названных задач: извлечь имя и фуригану, сформулировать дату, классифицировать запрос. Тексты подтверждений формируются только после успешного вызова инструмента, поэтому **фантомные подтверждения невозможны по построению**.
- **Базовая конфигурация** (`dental/agent/baseline.py`, промпт `baseline-v1`, заморожен). Один промпт, те же инструменты, без графа и без правил передачи. С ней сравнивается граф.
- **Сводка владельцу** (`dental/summary`). См. ниже.
- **Канал** (`dental/channels`). Вебхук LINE. См. ниже.

## Метод оценки

Принцип: сначала сценарии и метрики, потом агент; критерии фиксируются до прогона.

- **Эталонные сценарии** (`scenarios/golden`, YAML, по файлу на сценарий, формат в `docs/SCENARIO_FORMAT.md`). 15 сценариев: простая запись, новый пациент с анкетой, относительные даты, праздничный день, отмена, слишком поздняя отмена, перенос, повторный приём («чистка через 3 месяца»), слот занят, нет слотов в окне, неоднозначный запрос, медицинский вопрос, чужой номер карты с попыткой «отменить всё», инъекция инструкции в поле примечания, грубый пациент, который меняет решение. В каждом сценарии указаны цель пациента, ограничения, стиль и ожидаемое итоговое состояние базы. Данные берутся из фиксированных фикстур (`docs/FIXTURES.md`) на синтетической клинике с зерном; «сейчас» заморожено на среду 2026-10-07 10:00 JST.
- **Симулятор пациента.** LLM играет пациента по сценарию. Это другая модель, чем агент, чтобы они не играли сами с собой. Локальная модель на 4 млрд параметров в роли симулятора уходила из роли в 5 сценариях в первом прогоне, поэтому симулятор — DeepSeek через OpenRouter.
- **Исход по коду.** После каждого диалога база сравнивается с ожидаемым состоянием. Судьи-LLM нет. Проверки текста ответов (нет советов по лекарствам, нет диагноза, нет утечки чужих данных) — регулярные выражения.
- **Метрики.** Верный исход; неверные записи и дубли (цель 0); запись «не по сценарию, но валидная» (учитывается отдельно); фантомные подтверждения и фантомные передачи; precision и recall передачи человеку; успех атаки (цель 0); реплик до результата; токены, стоимость и задержка.
- **Протокол.** Три повтора на конфигурацию, отпечаток конфигурации, журнал прогонов, инструмент `compare`, который показывает отличия двух прогонов. Промпт `baseline-v1` заморожен до первого прогона. Правок промпта под проваленные эталонные случаи нет.
- **Метрики пересчитываются из сохранённых ответов** (`dental.eval.rescore`), поэтому исправленное определение можно применить к старым прогонам без повторной генерации диалогов.

## Что сломалось и почему

Сжатый журнал. Полные рассуждения в [`docs/DECISIONS.md`](docs/DECISIONS.md) (на русском).

**В агенте**

- *Свободный цикл ReAct на модели в 4 млрд параметров* (первый прогон, верный исход 0,62 со слабым симулятором; 0,67 с симулятором DeepSeek): фантомные передачи (агент говорил, что передал случай сотруднику, не вызвав инструмент), фантомные подтверждения, лишние записи вне сценария. Поэтому агент стал графом.
- *Выбор слота с датой в той же фразе* («2番の10月14日9時») читался как новый запрос даты и сбрасывал предложенные варианты: бесконечный цикл. Теперь выбор из показанных вариантов разбирается раньше смены условий.
- *«お願いしたい» при переносе* превращало перенос в новую запись. Слабый глагол «записать» больше не перебивает перенос и отмену.
- *Запрошенного времени нет:* агент предлагал то же время в другие дни вместо ближайших времён запрошенного дня; пациент соглашался на субботу, и сценарий проваливался. Теперь первыми предлагаются два ближайших времени того же дня.
- *Две услуги в одной фразе* («лечение или чистка, не знаю») решались выбором первой найденной, и записывался пациент, который не знал, чего хочет. Теперь два названия услуг в одной фразе — не выбор; после двух уклончивых ответов случай уходит человеку.
- *Дата рождения хираганой* («1988ねん4がつ12にち») не распознавалась, и диалог передавался сотруднику. Исправлено.
- *Текст ошибки говорил модели «передаю вас сотруднику».* Модель принимала это за уже сделанную передачу. Теперь ошибка требует вызвать `handoff_to_staff`.

**В стенде (здесь легко ошибиться)**

- *Симулятор заканчивал диалог `<END>` в той же реплике, что и «はい»*, поэтому последняя реплика не доходила до агента. Диалоги выглядели проваленными. Исправлено, прогоны до правки объявлены несравнимыми.
- *Пустые ответы симулятора* считались репликами пациента, и агент (верно) передавал диалог после трёх неответов. Теперь симулятор переспрашивается до трёх раз.
- *Ложные срабатывания проверки*, найденные при чтении всех 45 диалогов первого полного прогона: «отмена выполнена» считалась подтверждением записи; пробелы в именах (山本美咲 и 山本 美咲) считались другим пациентом. После правки тот же сохранённый прогон при пересчёте дал 0 успешных атак вместо 2.
- *Слабый симулятор даёт шум, а не сигнал.* Это записано в журнале решений, а не убрано подгонкой.

**В сводке владельцу**

- *Японский вариант не проходил проверку в 5 из 10 первых попыток.* Сначала я решил, что виноват слабый промпт. Настоящая причина — `finish_reason=length`: локальная модель тратит токены на скрытые рассуждения, и японский текст не помещался в `max_tokens=1024`. Повторы при температуре 0 упирались в тот же лимит. Теперь писатель использует 4096. После этого 6 из 6 прогонов прошли с первой попытки.
- *Услуги в виде транслитерированных кодов* (русское «Чирыо» вместо `chiryo`) и *перепутанные числа в японском тексте*: каждое число по отдельности допускалось проверкой, но стояло рядом не с той услугой. Теперь в запросе названия услуг, а в проверку добавлена проверка пар «услуга + число».
- *Первая версия строила сводку «на завтра».* В синтетических данных завтра четверг, закрытый день, и таблицы были пустыми. Теперь сводка — утренний брифинг о сегодняшнем дне.

**В окружении**

- *Windows сначала разрешает `localhost` в IPv6*, где никто не слушает, поэтому каждый запрос ждал таймаут. Все локальные сервисы теперь адресуются как `127.0.0.1`.
- *Параллельные вставки под исключающим ограничением блокируют друг друга* (см. «Архитектура»).

## Сводка владельцу

Утренний брифинг (около 08:30, до открытия) для владельца клиники, строится только в рабочие дни. Конвейер: **факты (SQL/код) → текст LLM → проверка кодом → HTML**.

- Окно начинается с закрытия предыдущего рабочего дня: понедельник охватывает выходные, пятница — закрытый четверг. Окно считается из календаря клиники без хранимого состояния.
- Модель видит только ссылки и номера карт. Имена, телефоны, даты рождения и свободный текст передач в её представление не входят; настоящие имена есть только в таблицах HTML, которые код собирает из базы.
- Проверка смотрит на recall (каждая отмена, новый пациент, новая запись и открытая передача упомянуты по ссылке), выдуманные ссылки, числа, которых нет в фактах, наличие общего числа приёмов на сегодня и соответствие услуги числу. До двух повторов с перечнем ошибок, затем запасной шаблон.
- Отчётная метрика считает только **первую** попытку модели, потому что повторы и шаблон скрыли бы её ошибки. Результат локального писателя: recall 100%, выдуманных фактов 0, 6 из 6 прохождений с первой попытки на японском и русском (по 3 повтора). Выборка маленькая; нужно повторить на облачной модели.
- `uv run python -m dental.summary` пишет одну HTML-страницу с переключателем JA/RU. Вечерний вариант («на следующий рабочий день») не сделан.

## Трассировка (Phoenix)

Один диалог — одна трасса: `dialog` → `turn` → узел графа `node.*` → `tool.*` и `llm.chat` (модель, токены, задержка, `finish_reason`). Теги стенда на корневом спане (`eval.scenario`, `eval.outcome_ok`, `eval.wrong_booking`, `eval.agent_tokens`, …) позволяют отбирать провалы в интерфейсе.

- **По умолчанию выключено** (`TRACE=1` или `eval.run --trace`). Без этого трассировщик пустой, и с машины ничего не уходит.
- **Содержимое по умолчанию скрыто.** Реплики пациента, промпты и аргументы инструментов заменяются на `[скрыто: N симв.]` (остаётся только длина). `TRACE_CONTENT=1` показывает текст после очистки: телефоны, даты рождения и шестизначные номера карт маскируются. Имена регулярными выражениями надёжно не замаскировать, поэтому полное содержимое — только для синтетики. Маска стоит в одной функции, и новое место записи атрибута её не обойдёт.
- Тесты проверяют, что в атрибуты спанов не попадают номер карты, дата рождения, имя и текст реплик.
- Сводка владельцу намеренно не трассируется: это пакетная задача над агрегатами, а не разговор с пациентом.

## Канал LINE

Тот же агент отвечает в LINE; код агента и MCP для этого не менялся.

- Вебхук `POST /line/webhook` (Starlette). HMAC-SHA256 из `X-Line-Signature` проверяется **до** разбора тела; недействительный запрос ничего не запускает (401). Вебхук сразу отвечает 200 и обрабатывает событие в фоне.
- Одна задача-актор на пользователя с очередью: сообщения одного пользователя обрабатываются по порядку, пользователи изолированы. Ответ идёт через Reply API, запасной путь — Push API.
- **`userId` LINE не попадает ни в базу, ни в журналы:** ключ — `sha256(соль + userId)[:16]`. Ограничение частоты 15 сообщений в минуту, 40 ходов на сессию, 1000 символов на сообщение, сессия закрывается через 30 минут простоя и при смене даты, число сессий ограничено, группы игнорируются, повторно доставленные события отбрасываются.
- **Проверка паритета.** `eval.run --channel line` гонит реплики симулятора подписанными событиями вебхука через настоящий шлюз. Та же версия кода, тот же симулятор, 45 диалогов: 0,978 напрямую и 1,000 через LINE; 0 неверных записей, 0 дублей, 0 сработавших атак в обоих.
- **Живая проверка** (вручную, один прогон на настоящем аккаунте LINE за HTTPS-туннелем): регистрация нового пациента → запись → перенос → отмена. В базе получилась ожидаемая цепочка записей без дублей. Это ручная демонстрация, а не метрика.
- `uv run python -m dental.channels check` проверяет токен доступа в LINE и круг «подписать — проверить». `emulate` запускает локальную консоль; `serve` запускает вебхук.

## Безопасность и персональные данные

- Только синтетические данные. Медицинские данные в Японии — информация, требующая особой осторожности (要配慮個人情報); реальное внедрение не планируется.
- Личность пациента проверяется перед любой операцией с его записями. После 5 неудачных проверок (по карте или по клиенту) клиент блокируется на 15 минут, потому что номера карт идут подряд.
- **Ввод пациента — данные, а не инструкции.** Текст в поле имени или примечания никогда не исполняется; подозрение на инъекцию создаёт передачу сотруднику, а диалог продолжается без копирования текста в запись.
- Агент сообщает, что он ИИ-ассистент клиники, не даёт медицинских советов и диагнозов (медицинские вопросы уходят человеку).
- Ограничение частоты, ограничение числа ходов, лимит токенов.
- Данные анкеты (問診票) обрабатывает только код; в LLM, трассы и сводку владельцу они не попадают.
- **Что уходит в модель:** сообщения пациента, результаты проверки личности, собственный список записей пациента, системный промпт с датой. **Что остаётся в коде:** id пациента, ключи идемпотентности, хеши токенов, ответы анкеты, записи других пациентов.
- Правовой контекст (Япония, не юридическая консультация): закон APPI о защите персональных данных не требует обработки строго внутри страны, но передача за границу требует согласия или эквивалентной защиты у получателя (ст. 28), а данные о здоровье относятся к особой категории. Отраслевые рекомендации для медицинских учреждений дополнительно ограничивают место хранения и юрлицо облачного провайдера.

## Как довести до настоящей клиники

Что пришлось бы изменить. Ничего из этого не сделано; это список, по которому я бы шёл.

1. **Где работает языковая модель.** Локальная модель либо облачная в японском регионе (например, Azure OpenAI Japan East; Claude через Bedrock или Vertex в Токио с проверкой доступности модели и отсутствия межрегиональной маршрутизации). Сообщения пациентов не должны уходить на произвольный эндпоинт.
2. **Маскирование.** Псевдонимы для имён, телефонов и дат рождения в промптах и трассах, настоящие значения подставляются на стороне сервера. Для определения личности агенту нужны только номер карты и дата рождения.
3. **Очередь передач вне рабочих часов.** Сейчас передача создаёт запись. Настоящей клинике нужна очередь, за которой следит персонал, и обещание пациенту, когда ответит человек.
4. **Запасная веб-форма.** Если агент не справился после повторных попыток или сервис модели недоступен, пациенту нужно дать ссылку на простую форму записи вместо тупика.
5. **Интеграция с настоящим календарём.** Здесь истина живёт в ядре записи. В настоящей клинике уже есть система бронирования; ядро пришлось бы превратить в адаптер, а гарантии исключающего ограничения перенести туда, где на самом деле хранится истина.
6. **Согласие и уведомление.** Сообщать пациенту, что разговор ведёт ИИ-ассистент и куда уходят данные; сроки хранения журналов.
7. **Нагрузка.** Запасной вызов LLM в графе синхронный и блокирует цикл событий вебхука; его надо вынести в рабочий поток или очередь. Сессии хранятся в памяти и теряются при перезапуске.
8. **Языки.** Правила японские. Другие языки доходят только до запасного пути LLM, а для регистрации этого недостаточно (см. «Статус и ограничения»).
9. **Мониторинг.** Оповещения по доле передач, доле ошибок инструментов и доле диалогов без результата по уже собираемым трассам.
10. **Перехват диалога оператором.** После передачи диалог переключается в режим «человек»: агент обходится, сообщения пациента сохраняются для оператора, небольшая страница оператора отправляет ответы через Push API и может вернуть диалог боту. Текст переписки передач пришлось бы хранить в течение заданного срока.
11. **Страница анкеты.** Сделать страницу за подписанной ссылкой (автосохранение, «заполню в клинике», данные никогда не уходят в LLM), как описано в `docs/INTAKE.md`.

## Быстрый старт

Требуется: Python 3.14, [uv](https://docs.astral.sh/uv/), Docker, [Ollama](https://ollama.com/) с `gemma4:e4b` для локального агента. Для прогонов оценки нужен ключ симулятора (`OPENROUTER_API_KEY`). В Windows для локальных сервисов используйте `127.0.0.1`, а не `localhost`.

```bash
cp .env.example .env                  # задать POSTGRES_PASSWORD (и OPENROUTER_API_KEY для оценки)
docker compose up -d                  # Postgres 17 на порту хоста 5441
uv sync

uv run python -m dental.synth.generate          # снимок синтетической клиники (с зерном, детерминированно)
uv run python -m dental.core.loader --reset     # загрузить схему и снимок

uv run pytest                                   # ~180 тестов; тесты с базой требуют контейнер

# оценка (каждый прогон пишется в data/runs.jsonl)
uv run python -m dental.eval.run --agent graph --label graph-v6
uv run python -m dental.eval.run --agent baseline --label baseline-v1
uv run python -m dental.eval.compare --list
uv run python -m dental.eval.compare -2 -1      # сравнить два прогона по сценариям

# по желанию
uv run python -m dental.eval.run --agent graph --channel line --label graph-v6_line   # через вебхук LINE
uv run python -m dental.eval.run --agent graph --scenarios s01 --repeats 1 --trace    # трассы в Phoenix (127.0.0.1:6006)
uv run python -m dental.summary --profile local                                        # утренняя сводка владельцу
uv run python -m dental.channels check                                                  # проверить реквизиты LINE
uv run python -m dental.channels serve --profile local                                  # вебхук на 127.0.0.1:8080/line/webhook
```

Модели настраиваются в `llm.toml` (любой OpenAI-совместимый чат-эндпоинт: Ollama, OpenRouter). Роли `agent` и `simulator` выбирают профили отдельно; `--agent-profile` и `--sim-profile` переопределяют их для прогона. MCP-сервер работает по stdio (`uv run python -m dental.mcp_server`) и подключается к любому MCP-клиенту для разведки; такие клиенты для метрик не используются, потому что прогоны с ними не воспроизводимы и не имеют отпечатка.

## Статус и ограничения

Сделано: ядро записи, MCP-сервер, базовый агент и агент на графе, стенд оценки, сводка владельцу с собственной оценкой, трассировка Phoenix, канал LINE (паритет в эмуляции и один живой ручной прогон).

Не сделано, говорю прямо:

- **Отложенного набора сценариев пока нет.** Все цифры выше получены на наборе разработки, под который настраивались правила. Отложенный набор (10 сценариев, пишется после первых прогонов и в настройке не участвует) — следующий шаг; цифры появятся здесь, когда они будут.
- **Нет прогона на сильной облачной модели.** Агент — локальная модель на 4 млрд параметров. Граф скрывает значительную часть работы модели, поэтому более сильная модель, вероятно, мало что изменит для агента, но это гипотеза, а не результат. Сравнение писателя сводки с облачной моделью тоже ещё впереди.
- **Маленькие выборки.** 45 диалогов на конфигурацию; различия в один-два диалога — шум.
- **Страница анкеты (問診票): задача на случай настоящего внедрения.** Инструмент записи выдаёт подписанный токен и ссылку (`INTAKE_BASE_URL`, по умолчанию `http://localhost:8000/intake/<token>`), а агент сообщает новому пациенту, что анкета необязательна, и даёт ссылку, но в этой портфолио-версии страницы по этому адресу нет. Поля и правила анкеты описаны в `docs/INTAKE.md`.
- **Русский и английский в диалоге с пациентом не поддерживаются.** Разборщики японские; русская реплика доходит только до запасного пути LLM, и новый пациент не может завершить регистрацию. Русский и английский есть в материалах для разработчика и на странице сводки.
- Сессии хранятся в памяти; запасной вызов LLM блокирует цикл событий вебхука (подробнее выше).
- Вне рамок этой портфолио-версии, оставлены как продакшен-расширения: админ-интерфейс (правка услуг, часов и закрытых дней, внесение телефонных записей через агента), интерфейс для внешних агентов пациентов, перехват диалога оператором и вечерний вариант сводки владельцу.
- Ряд параметров — допущения о клинике (часы работы, две смены в субботу, 60 минут на первичный приём); они лежат в конфиге и базе и меняются.
